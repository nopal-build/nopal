# ADR-029 — A seed packet is rows, not a folder, and sowing asks before it names anyone.

**Status:** Accepted, 2026-09-30. Builds on ADR-023, ADR-024, ADR-025 and ADR-027.

**Context.** ADR-027 made seeded history a kind of entry, but the seed folder was built by hand in the vault and pushed with the CLI. For it to last, anyone on a project has to be able to hand over what they have (a thread, an email export, a PDF), and something has to do what was done by hand for Campbell: split it by the day things were said, keep people's words exactly, leave out chatter and AI framing, and write plain facts as Noted. The named disappointments: a client's words under the wrong name, and a guide facing forty questions for one packet.

**Decision.**
- **Seeding happens in rounds.** A project started in the Maker opens with one (`startProject`); a Guide opens another when a new person, a new phase or a batch of information calls for it, and ends it. While a round is open everyone with a role on the project has a seed packet on the project page. The round is a row in `seed_rounds`; a packet shows by the round's state at read time, so nothing is stamped on people and someone added after the round ended has no packet until the next.
- **A packet is rows, never a Vault folder.** The guide asked for a system folder under Syncs. Three things rule it out: sync-knowledge describes every file under `Syncs/` on every run; every folder under a project carries the project's `shared_with`, so Crafters and Observers would see every packet in the Vault; and a project-view reset deletes any project child that is not skills, syncs or graph. A packet's files are rows in `seed_packet_files`, keyed by project, person and round, with the bytes in storage (text inline). One route adds to the caller's own packet (any role, a Client included); one route serves a file, to the person who added it and the project's Guides and nobody else, with a 404 for the rest. Nothing else can reach what nothing else knows exists (ADR-024's lesson: a permission list only decides what nothing else already grants).
- **Sow is a Guide's button and its own job.** `POST /api/graphlog/sow` enqueues `sow` on the GraphLog queue; it is never part of `run`. Each file is read once (`sown_at`); the same name with different bytes is a new file. A text file goes to the model; a PDF or a photo is kept as a seed document as it is, on the bytes it already has, authored by whoever added it. Ending the round closes the packets at once and sows what is left.
- **The model proposes; code checks and places.** The model says what a file is, and for a conversation proposes each message, whole, with its day, its speaker, and whether it is sure of each (`SOW.md`, written for Opus 5.5, the model the week grid chose). Sow gives a file the shape of a daily log and nothing more; what earns a node, and how a message splits into ideas, is sync-graph's call, made once, with the graph in view. A first draft had sow selecting statements too, which was the graph stage's judgment done early and weaker. Code refuses any line that is not in the file word for word, then places each (`planSow`), first rule that applies: already in that day's seed, skipped; matches a Card on the project within two days either side (`matchesCard`: four in five of a line's four-word runs), held out; no sure date, held out; no sure speaker or a speaker nobody knows, written under Noted as nobody's words; otherwise under the speaker. A known speaker is a project member or a name the seed already speaks under.
- **The day a file was added settles a date with no year.** A thread says "8/5". Without an anchor every such date is an estimate, and the first live packet turned eight lines into six questions. Code tells the model the added day; a month and day with no year is the latest one on or before it, and that is the file stating the date.
- **An unsure line costs a yes or no, never a guess.** Each held or Noted line raises a question in `seed_questions`, shown to Guides in the Suggestions tab as a third kind with its own meaning for each answer: "who said this?" yes moves the line from Noted to the person; "already logged?" yes leaves it out, no puts it in; "when was this?" yes puts it on that day. The answer edits that one day's seed file, which changes that day's hash, so the next run re-extracts that day alone. A wrong name never reaches the page, only a missing one.
- **A packet adds to a day; nothing overwrites.** `mergeSeedDay` appends under the speaker in a group with the packet's own `- src:` line and skips a line already there. The CLI push, which replaces a day by name, refuses a day a sowing has written to and names it. An admin's seed wipe also deletes the questions and clears every `sown_at`, so Sow rebuilds the seed from the packets.

**Why it looks removable.** A packet could be a folder under Syncs and the privacy rule a check in `canReadFile`. The Vault tree, the children route, the download manifest, the zip and the search all list a project folder's files by `shared_with`; each would need the same exception, and the first one missed shows a client's raw email to a Crafter.

**Limits.** What to leave out of a packet is the uploader's; the stage is told no privacy rule. The week grid scored the stage against cards that already name every speaker and date, so it measured chatter and Noted, not attribution from a raw thread; the first real packet is that test. The Card-match threshold and the question kinds are values someone maintains. Raw files stay after a round ends, for their uploader and the Guides.

**How you'd know.** A Crafter, an Observer or another Client opens a packet file; a packet file shows in the Vault or gets described by sync-knowledge; pressing Sow twice reads a file twice or doubles a line; a line appears under a name the file did not plainly give; one small packet raises a page of questions; a push erases sown lines.

**Test.** `webapp/app/tests/graphlog/sow.test.ts` and `seed.test.ts` (the merge, the placement rules, the Card match, the verbatim check, the scorer), and `fruits/scripts/campbell-walk.ts` (the seed packets section) against a running stack.
