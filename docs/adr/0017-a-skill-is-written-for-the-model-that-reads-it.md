# ADR-017 — A skill is written for the model that reads it.

**Status:** Accepted, 2026-09-18

**Context.** A GraphLog skill (`GRAPH.md`, `GRAPH_STRUCTURE.md`, `EFFORTS.md`, `VOICE.md`, `KNOWLEDGE.md`; seeded from the template strings in `graphLogDefaults.server.ts`) is read at runtime by one specific model at one specific effort, set per stage in `STAGE_DEFAULTS` (`anthropicProvider.server.ts`), and never by the model or the person that wrote it. The 2026-09-11 grid (five model and effort configurations, three test days, one full README build) and the 2026-09-14 held-structure control found that a literal reader turns an unstated rule into a per-run coin flip, that a stronger reader does worse when handed method it would have inferred, and that lowering effort lowers the reader. On that basis one commit (`678dae9`) moved two skills in opposite directions: `PROJECT_VIEW.md` (now `EFFORTS.md`) was rewritten at 40% of its length as goals and boundaries for an inferring reader, and `GRAPH.md` got longer for a literal one: thresholds instead of leans, a two-step list test, a stated unit. Where prose alone still did not move the literal reader, the rule went into code (`listSplitBounce`, `reviewClusterWrite`), because the tool result is the channel that reader answers to. None of that reasoning was in the repo. Two days later a different file, the agent-facing `.agents/skills/graphlog/SKILL.md`, was rewritten from 1,575 lines to 714 on the general reasoning that long skills perform badly. That cut turned out to be mostly sound (what left was build history, restatement, and text that contradicted the code), and it touched no runtime skill. But nothing written down would have stopped the same reasoning being applied to `GRAPH.md`, where it would have removed exactly what the grid put there.

**Decision.** Each runtime skill is sized to what its own reader will not infer: a literal reader gets the unit, the threshold and the test written out; an inferring reader gets intent and boundaries and is not handed method. A rule code can enforce is enforced in code and the skill says code owns it. Changing which model or effort reads a skill is a reason to reread the skill, and the reverse. Length is reported wherever a skill changes (the Janitor, ADR-018) and is never enforced, up or down.

This record covers the runtime skills. It makes no claim about documents a coding agent reads, where nothing has been measured.

**Why it looks removable.** A long skill file reads as bloat, and general knowledge says long prompts degrade. Cutting one looks like maintenance, the pipeline still runs, and the diff looks like an improvement to anyone who was not in the round that made it long. The opposite error looks just as reasonable: adding worked method to `EFFORTS.md` looks like being thorough.

**How you'd know.** Not from the diff. Node-count spread widens across identical runs on the marginal day. Lists stop splitting consistently. Photos become nodes on one run and not the next. The README starts padding or inventing. All of it shows up as output drift weeks later with no obvious cause. (Of these, only node count is counted per run today. List-split bounces and photo nodes are not, and a reader of this record should not assume they are being watched.)

**Test.** Owed, not in place. The intended test: a changed skill is run on the model that reads it, across the three test days (2026-08-26 busy, 2026-08-19 medium, 2026-08-18 marginal), twice per configuration, and read side by side against saved outputs from the last validated version; a change that moves the marginal day the same way twice is a change, one run is not. No baseline outputs are saved as of this date: the 09-11 and 09-14 cell outputs are gone from disk, and their readings survive only as the `STAGE_DEFAULTS` doc comment and its pinned test (`loadBearingBehaviors.test.ts`, "defaults: Sonnet medium for extraction..."). The baseline is deliberately deferred until projects have run long enough to test against; the current model picks are accepted as a good match until then. What holds today is narrower and checkable: `webapp/app/tests/janitor.test.ts` fails when a number, tool or field a skill states stops matching the code, and the Janitor puts every skill change in front of the other person with its size on both sides.
